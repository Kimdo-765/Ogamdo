# Live-fire v2 — 4-agent 재설계

오퍼레이터 결정 (2026-09-11):
- v2는 **별도 모드로 병행**. 기존 live-fire 경로는 폴백으로 살려 둔다.
- 개발 기준 번들은 현재 base.zip. 기존 실행은 알려진 취약점 중 일부만 찾았다.

## 역할 (오퍼레이터 사양)

- **plan agent** — base 소스를 받아 N개 취약점 식별. 식별되는 대로 blueteam agent를
  생성하고 정보 인계(취약점 / 연관 소스 / 패치 방향성). operator feedback에 따라
  추가 취약점 식별.
- **validator agent** — base 기준 정상 요청/응답 쌍 생성 → plan agent에 공유.
  blueteam이 패치본을 넘기면 그 쌍이 여전히 유효한지 + 가용성 검사.
  통과하면 repo agent에 인계.
- **blueteam agent** (×N) — plan이 생성. 인계받은 정보로 패치. validator에 검사 요청.
- **repo agent** — 검사 통과분을 인수해 **패치 통합본** 재생산, 이력 관리, 레포트 생산,
  오퍼레이터에게 버전별 제공.

## 아키텍처 결정 (사양에서 도출, 별도 질의 없이 확정)

1. **격리/병합** — blueteam N개는 각자 base의 **자기 사본**을 패치한다. 공통 base
   대비 독립 diff가 나오고, repo agent가 병합해 통합본을 만든다. 동일 파일 충돌은
   드물지 않으므로 **패자를 병합 트리 위에 직렬 재적용 후 재검증**한다. 조용히
   버리지 않는다.
2. **통합본 재검증** — 개별로 안전한 두 패치가 합쳐서 깨질 수 있다. 오퍼레이터가
   업로드하는 것은 repo agent의 산출물이므로 통합본은 반드시 다시 validator를 탄다.
3. **기존 loop 재사용 안 함** — `live_fire_patch_loop`의 게이트(`_finding_errors`,
   `_location_matches_diff`, report 스키마, `terminal_ready`)는 "한 에이전트가 한
   candidate 트리를 편집"을 전제로 한다. v2는 N개 독립 diff + 병합이라 불변식이
   다르다. `live_fire_workspace`(ingest/manifest/build_patched_zip)와
   `live_fire_verifier`의 Docker 경계만 재사용한다.

## Phase 1 — compose 스택 런타임 (지금 짓는 것)

이것이 없으면 validator agent가 존재할 수 없고, 나머지 어떤 것도 검증되지 않는다.
독립적으로도 유용하다 — 계속 P0로 올려둔 "SLA benign 검증"이 바로 이것이다.

### 번들 compose에서 흔히 충돌하는 키

번들 compose는 흔히 최상위 `name:`과 서비스별 `container_name:`을 고정하고,
앞단 프록시만 host 포트를 publish하며, 볼륨·네트워크에 고정 이름을 준다.
하나라도 있으면 같은 번들의 두 스택은 공존할 수 없다 — 아래 격리 변환이
이를 전부 벗겨낸다.

### 확인된 차단 요소

| 사실 | 영향 |
|---|---|
| worker에 `docker compose` 플러그인 없음 (`docker-ce-cli`만 설치) | **worker 이미지 재빌드 필요** |
| worker에 PyYAML 없음 | compose 자체를 파서로 써서 회피 (아래) |
| `/usr/local/bin/docker`는 memguard 심이고 범위가 `run`/`create` 뿐 | `compose up`은 심을 우회 → **캡·잡 라벨이 안 걸림** |
| `reap_job_siblings`는 컨테이너·네트워크만 라벨로 회수 | 볼륨·이미지는 안 쓸림 → `down -v --rmi local` 필수 |

### 설계

**PyYAML 없이 파싱** — compose를 자기 자신의 파서로 쓴다:
1. `docker compose -f docker-compose.yml config --format json` → 완전히 해석된 모델
   (env 보간, `depends_on` 정규화, build context 절대경로화까지 compose가 해 줌)
2. Python dict로 변환 (json은 표준 라이브러리)
3. `json.dump`로 `stack.yml`에 기록 — JSON은 YAML의 부분집합이라 compose가 읽는다
4. `docker compose -f stack.yml -p <project> up -d`

PyYAML로 compose 의미론을 추측하는 것보다 훨씬 견고하다.

**격리 변환** (`stack.yml`을 만들 때 적용, 이것이 mutation test 대상):
- 최상위 `name` 제거 → `-p <project>`가 결정
- 서비스별: `container_name` 삭제, `ports` 삭제(기록해 둠), `restart: "no"`
- 서비스별 주입: `mem_limit`, `cpus`, `pids_limit`,
  `labels: {hextech_ctf_tool_job_id: <id>}`
- 네트워크/볼륨에도 동일 라벨. 볼륨은 `name:` 키 삭제 →
  compose가 `<project>_<vol>`로 자동 명명 → 격리 무료
- `ports`에서 벗겨낸 정보가 **entrypoint map**이 된다:
  `{<앞단 서비스>: [<target 포트>]}` — 코퍼스가 때릴 대상

**도달 방법** — 퍼블리시 포트 없이, 스택 네트워크에 붙인 **프로브 컨테이너**에서
`http://<앞단 서비스>:<포트>/...`. `container_name`을 지웠으므로 DNS 별칭은 서비스 키다.
기존 verifier가 이미 쓰는 방식과 같다.

**정리** — `finally`에서 `compose down -v --rmi local --remove-orphans`.
번들 전체 서비스 × N스택은 지금까지 본 어떤 것보다 빠르게 샌다.

### Phase 1 범위 (여기까지만)

1. 격리 변환 + `up`/`down`
2. base 대비 **코퍼스 캡처** (정상 요청/응답 쌍)
3. 패치 트리 대비 **코퍼스 재생** + 차이 판정
4. mutation-tested 스위트

plan/blueteam/repo agent는 Phase 1에 없다.

### 라이브 검증 — 실제 번들, 총 5개 스택 기동/철거

| 확인 항목 | 결과 |
|---|---|
| 번들 전체 스택 기동 | 첫 회와 빌드 캐시를 쓴 재기동 모두 성공 |
| 준비 게이트 | 3연속 정상 응답으로 통과 |
| 코퍼스 캡처 | 요청 전부, 실제 HTML 응답 |
| **캡이 실제로 걸렸는가** | `docker inspect` 전 컨테이너: mem=1073741824, nano_cpus=2e9, pids=512 |
| **패치가 이미지에 도달하는가** | base·patched 각 이미지가 서빙하는 파일이 자기 트리의 디스크 파일과 바이트까지 일치 |
| 비교기 오탐 (base A vs B) | 전 요청 검사, findings **0** |
| 누수 | 컨테이너·네트워크·볼륨·이미지 전부 0 |

### 비교기가 실제로 맞힌 것

어떤 응답은 base와 patched가 **길이는 같은데 sha가 다릅니다**. 비교기는
이것을 findings 0으로 판정했는데, 실제 diff를 뜯어보니 차이가 정확히
**요청마다 새로 찍히는 값**뿐이고 base1↔base2에서도 똑같이 흔들립니다.
그런 값은 손으로 쓴 무시 목록으로는
결코 못 맞혔을 값입니다. 번들을 두 번 캡처해 스스로 알아낸 것이 값을 했습니다.
동시에 패치가 실제로 바꾼 응답은 전혀 가리지 않았습니다.

### 설계상 바로잡은 것

첫 구현은 "patched의 각 줄이 base 두 캡처의 줄 집합에 있는가"로 추가를
판정했는데, autoincrement처럼 흔들리는 줄이 patched에서 **제3의 값**을 가지면
그것을 "추가된 줄"로 오탐합니다. 테스트(D1)가 잡았습니다. 지금은 spine 앵커
사이의 **간격(gap)** 단위로 판정합니다:

- 두 base 캡처가 그 간격의 **내용까지 같으면** → patched도 같아야 함
- 내용은 다르지만 **줄 수가 같으면** → 줄 수가 오라클로 남음
  (세션 id 옆에 배너를 끼워 넣는 수법이 여기서 걸립니다 — D10)
- 줄 수까지 다르면 → 그 간격은 판정 불가

### 최종 라이브 판정 (게이트 수정 후)

코퍼스에 **인증 세션**이 들어가면서 로그인 뒤 페이지까지 실제로 검사합니다.

```
base 자기검사 (A vs B):  ok=true  checked=N/N  findings=0  unstable=0  broken=0
```

**오탐 0**입니다(base A vs B, N/N). 가상의 예를 들면, 패치가 정적 파일을 고칠
경우 그 파일을 직접 받는 요청은 디스크와 같은 새 바이트를 돌려주므로 비교기는
그것을 차이로 잡습니다.

> **오퍼레이터 판단이 필요한 지점**: 패치가 정적 파일을 고친 경우, "그대로 서빙되는 파일이 바뀐 것"이 SLA 위반인지는
> 공격 서버의 SLA 체커가 그 파일을 받아서 비교하는지에 달려 있습니다. 페이지
> 동작만 본다면 위반이 아니고, 자산 해시를 본다면 위반입니다. 지금 게이트는
> 이것을 **하드 실패**로 잡습니다. Phase 2에서 이 종류를 "검토 필요"로 낮출지
> 결정이 필요합니다.

### Phase 1이 답하지 못하는 것

손으로 쓴 코퍼스는 **런타임을 증명하기 위한 것이지 최종 코퍼스가 아닙니다**.
앞단 프록시를 거치지 않는 서비스가 있다면 그런 서비스는 여전히 직접 프로브되지
않습니다(코퍼스는 앞단 프록시만 때림). 코퍼스 생성은 **validator agent가 소스를 읽고 하는 일**입니다.

그런 서비스도 프로브 컨테이너에서 닿기는 하지만 앞단 프록시를 거치지 않으므로,
내부 서비스를 직접 검사하려면 별도 요청이 필요합니다.

## Phase 1 이후 바로잡은 것 세 가지 (같은 날, 검토 후)

### 1. 준비 게이트가 MySQL을 못 보고 있었다 — 가장 중요

2xx는 준비 완료가 아닙니다. `docker-entrypoint-initdb.d` 시딩이 끝나기 전에는
DB 기반 목록 페이지가 빈 목록으로 200을 줄 수 있고, 로그인은 평범한 실패 화면으로
답해 틀린 비밀번호와 구별되지 않을 수 있습니다. 시딩이 끝나면 같은 목록이 훨씬 긴
본문으로 200을 줍니다. 200을 준비 완료로 읽던 기존 게이트는 그 시딩 창 안에서
통과했고, **위의 Phase 1 라이브 결과는 전부 시드 이전 상태를 기준으로 잡은 것**입니다.
판정이 틀리진 않았지만(세 런이 똑같이 시드 전이라 서로 일치) 검사 대상이
엉뚱했습니다.

더 나쁜 것은 이것이 **겹쳐서 숨는다**는 점입니다. 그 창 안에서 뜬 두 base
캡처는 서로 일치하므로 calibration은 코퍼스를 "완벽히 안정적"이라고 판정하고,
SLA는 반쯤 초기화된 시스템을 기준으로 선의로 검사됩니다.

첫 수정은 신호를 성공이 아니라 **HTTP 안정성**으로 바꾸는 것이었습니다 —
status와 본문 길이가 연속 폴에서 변하지 않아야 통과. **그래도 못 잡았습니다.**
시드 전 상태 자체가 완벽히 안정적이기 때문입니다: 빈 목록은 언제 찍어도
똑같이 200·같은 크기로 렌더됩니다. 게이트는 여전히 시딩 창 안에서 통과했습니다.

진짜 신호는 다른 곳에 있었습니다. 공식 mysql 이미지는
`docker-entrypoint-initdb.d`를 **`--skip-networking`으로 띄운 임시 서버**에서
돌리고, 스크립트가 끝난 뒤에야 진짜 mysqld를 exec합니다. 즉 "3306을 열 수
있는가"는 "시드가 끝났는가"의 근사치가 아니라 **같은 사건**입니다. 시딩이 도는
동안 `mysql:3306`과 `mysql:33060`은 닫혀 있고, 포트가 열린 뒤에 통과한 게이트는
시드 후 상태를 봅니다.

그래서 `wait_ready`는 **TCP 게이트를 먼저** 돌립니다. 각 서비스가 이미지의
`EXPOSE`로 선언한 포트에 실제로 연결이 되어야 합니다 — compose 파일이 아니라
이미지에서 읽는 이유는 DB 서비스가 흔히 포트를 하나도 publish하지 않기
때문이고, 그것이 바로 HTTP 게이트가 못 보는 이유입니다. HTTP 안정성 폴은
그 뒤에 2차 게이트로 남습니다.

### 4. 프로브 출력이 256KiB에서 조용히 잘렸다

시드가 끝난 첫 실제 코퍼스를 잡자
`live_fire_verifier`의 공용 러너가 정확히 262144바이트에서 JSON을
잘랐고, 원인을 가리키는 것 없이 `JSONDecodeError`로만 올라왔습니다.
프로브 전용 예산(64MiB)과 컨테이너 내 gzip 압축(HTML은 약 10배 압축)을 넣고,
잘린 캡처는 **이름을 불러 거부**합니다 — 반만 읽힌 캡처를 신뢰하느니 실패하는
편이 낫습니다.

### 2. `checked=0`인데 `ok=True`는 증거 없는 통과였다

불안정 요청은 finding을 내기 전에 건너뛰므로, 전부 불안정하면 "다 흔들렸으니
SLA는 지켜졌다"가 됩니다. `min_checked` 바닥을 `compare()` 안에서 강제합니다 —
잊어버리는 호출자가 바로 아무것도 아닌 것에 녹색불을 켜는 쪽이기 때문입니다.

또 `unstable`과 `broken`을 분리했습니다. base 캡처가 서비스에 **닿지도 못한**
것은 비결정성이 아니라 깨진 코퍼스 항목이고, 이것을 관용하면 코퍼스가 한
요청씩 썩어가는 동안 판정은 계속 녹색입니다.

### 3. 쿠키 없이는 로그인 뒤 페이지를 검사할 수 없었다

로그인 뒤 페이지는 익명 요청으로는 검사할 수 없었습니다. `CorpusRequest.session`을
추가했습니다 — 같은 이름이면 쿠키 잼 공유, 빈 이름이면 요청마다 새 잼(익명
페이지가 로그인을 물려받지 않도록).

라이브 증명: 같은 세션의 두 번째 요청에 `Set-Cookie`가 오지 않고(서버가 세션을
인식), 이름이 다른 세션끼리는 서로 다른 세션 쿠키를 받으며, 익명 요청은 매번
새로 받습니다. 로그인에 쓰는 계정 정보는 테스트 하니스에만 두고
리포지토리에는 커밋하지 않습니다.

## 동시 스택 실측 — Phase 2의 fan-out 상한을 정하는 숫자

4-agent 설계는 blueteam N개가 각자 자기 패치를 검증하는 것을 전제합니다. 그런데
지금까지의 라이브 런은 전부 **의도적으로 순차**였으므로, 이 전제는 한 번도
시험된 적이 없었습니다. base 2개 + patched 2개를 동시에 띄웠습니다.

```
lfv2c1 base    up ✓  ready ✓  build=base     ✓
lfv2c2 patched up ✓  ready ✓  build=patched  ✓
lfv2c3 base    up ✓  ready ✓  build=base     ✓
lfv2c4 patched up ✓  ready ✓  build=patched  ✓
격리: 네 스택 모두 자기 빌드를 서빙 (교차오염 없음)
```

**메모리는 제약이 아닙니다** — 4스택을 동시에 띄워도 호스트 RAM에는 여유가
컸습니다. 서비스당 1 GiB 캡은 예약이 아니라 천장입니다.

**제약은 네트워크입니다.** 스택마다 번들의 네트워크 수만큼 브리지를 쓰고, docker
기본 주소 풀에는 상한이 있습니다. 그래서
**동시 스택의 실질 상한 ≈ (주소 풀 − 이미 쓰고 있는 네트워크) ÷ 스택당 네트워크 수**이고,
다른 잡의 챌린지 컨테이너 몫을 남긴 값이 안전선입니다.

이건 튜닝 값이 아니라 **아키텍처 결정**입니다: Phase 2의 blueteam fan-out에는
슬롯 예산과 대기열이 필요합니다. 지금 번들 규모면 슬롯 안에 들어가지만, 상한이
있다는 사실을 설계가 알고 있어야 합니다. 이 프로젝트는 이미 한 번 당했습니다 —
`worker/docker_memguard.sh`가 기록하듯 2026-08-02에 고아 네트워크 3개가
발견됐고, 누적되면 새 잡 셋업이 "could not find an available, non-overlapping
IPv4 address pool"로 아예 실패합니다.

관련해서 `reap_job_siblings`를 **볼륨과 이미지까지** 쓸도록 넓혔습니다.
`live_fire_stack`은 `compose down -v --rmi local`로 스스로 치우지만 그건
**teardown이 돌 때만**입니다. 하드킬된 잡은 그 경로를 건너뛰고, 그게 바로
이 스윕이 존재하는 이유입니다. 라벨은 이미 붙어 있었고 보기만 안 하고
있었습니다.

## Phase 2 결과 — validator agent (완료)

`modules/live_fire_validator.py` + `scripts/test_live_fire_validator.py`
(baseline 31 검사 / mutation 19개 전부 포착).

### 라이브 판정 — 실제 번들 + 실제 패치, 코퍼스(인증 세션 포함)

```
base를 자기 베이스라인으로 검증 :  ok=true  N/N  findings 0
patched 검증 (run 1)            :  ok=true  N/N  unexplained 0
patched 검증 (run 2, 동일 입력)  :  ok=true  N/N  unexplained 0
```

**explained**는 패치의 `changed_paths`에 든 파일을 바이트 그대로 돌려주는 요청의 차이를 말하며,
Phase 1 게이트였다면 하드 실패였을 종류입니다. validator는 이제 그것을
**패치가 한 일**로 분류하고 패치를 승인합니다. 이 분류가 없으면 서빙되는
파일을 직접 고치는 수정은 전부 자기 validator에게 거부당해 repo agent에 도달하지
못합니다.

### 면제는 위조할 수 없다

`serves`는 "이 요청은 이 파일을 그대로 돌려준다"는 **에이전트의 주장**입니다.
주장만으로 면제가 되면, 면제를 원하는 에이전트는 모든 요청에 그것을 붙입니다.
그래서 `establish()`가 base 응답을 디스크의 파일과 **바이트 단위로 대조**하고
맞지 않는 주장은 버립니다. 렌더된 페이지는 파일이 될 수 없으므로, 구멍을
넓히는 것은 불가능하고 잃는 것만 가능합니다.

규칙은 그래서 이렇습니다:
- 정적 자산 요청이 바뀌었고 그 파일이 `changed_paths`에 있다 → **설명됨**
- 렌더된 페이지가 바뀌었고 그 소스가 `changed_paths`에 있다
  → **여전히 위반**. 공격 서버의 benign 페이로드가 보는 것은 파일의 바이트가
  아니라 **렌더 결과**입니다.

### 검토에서 잡힌 결함 넷 (테스트를 쓰기 전에)

1. **네임스페이스 불일치.** 프롬프트 예시는 `fo_src/...`인데
   `_verify_serves`는 번들 디렉터리(이미 `fo_src`) 기준으로 붙여
   `fo_src/fo_src/...`가 됐습니다 → 해석 실패 → 주장 폐기 →
   **모든 정적 자산 수정이 다시 거부**. `serves`가 막으려던 바로 그 버그를
   경로 접두사 하나로 재현하는 것이었습니다. 세 경계(에이전트가 읽는 목록 /
   에이전트가 쓰는 주장 / `changed_paths`)를 전부 **워크스페이스 루트**로
   통일했습니다 — `DiffRecord.path`가 이미 쓰는 네임스페이스이고,
   bf8d00c76ed8의 `result.json`에서 실측한 값입니다.
2. **프로젝트 이름이 고정**이라 동시 실행되는 두 v2 잡이 `lfv2basea`를 서로
   빼앗았습니다. 이제 이름에 job_id가 들어갑니다.
3. **`except (StackError, Exception)`** — 의도는 좁았는데 코드는 전체였습니다.
   우리 쪽 `AttributeError`가 "blueteam 패치가 가용하지 않음"으로 보고되어
   멀쩡한 패치가 조용히 버려집니다. 두 종류로 좁혔습니다.
4. **establish 단계 커버리지 바닥 부재.** validate 단계 바닥은 *살아남은*
   요청 기준이라, 40개 제안 중 30개가 떨어지면 10개의 8개를 요구하면서
   "전부 검사함"으로 보고됩니다.

### 관측된 flakiness 하나, 추측 없이 처리

같은 입력에 대한 두 번의 실행이 **엇갈렸습니다**: 한 번은
일부 페이지에서 여러 건을 unexplained로
보고했고, 다른 번은 하나도 없었습니다. base를 자기 베이스라인으로 검증한
결과는 두 번 다 깨끗했습니다. base **쌍** 하나로는 페이지의 변동성을 과소평가할
수 있고 — 우연히 일치한 두 캡처가 "이 필드는 고정"이라고 가르칩니다 — 그
대가를 패치가 뒤집어씁니다.

원인을 추측해 덮는 대신 **확인 패스**를 넣었습니다(`CONFIRM_PASSES = 2`):
이미 떠 있는 스택에 프로브 컨테이너 하나를 더 돌려 코퍼스를 다시 잡고,
**모든 캡처에서 재현된 finding만** 믿습니다. 스택 준비 시간에 비하면 작은
비용입니다. 정직하게 말하면, 재실행에서 flake가 재현되지 않아
**이 장치가 실제로 발동하는 것은 아직 못 봤습니다** — 보험입니다.

## Phase 3a 결과 — repo agent 병합 엔진 (완료)

`modules/live_fire_repo.py` + `scripts/test_live_fire_repo.py`
(baseline 27 검사 / mutation 16개 전부 포착).

v1은 한 에이전트가 한 candidate 트리를 편집했으므로 "패치"와 "트리"가 같은
물건이었고 통합이라는 문제가 존재하지 않았습니다. v2는 blueteam N개가 각자
자기 base 사본에서 작업하므로 — 그래야 서로 덮어쓰지 않습니다 — 여기 도착하는
것은 **공통 base에 대한 독립 diff N개**입니다. 두 개가 같은 파일을 건드리는 건
드문 일이 아닙니다: 취약점은 한 디렉터리에 몰리기도 하고 파일 하나에
둘이 들어갈 수도 있습니다.

### 규칙

- 한 제출만 건드린 파일 → 그대로
- 여러 제출이 건드렸으나 **영역이 겹치지 않으면** → 둘 다 병합
- 겹치면 → 결정적 순서(취약점 ID)로 첫 번째를 채택하고 나머지는 **보류**

**보류지 폐기가 아닙니다.** 조용히 버려진 패치는 오퍼레이터가 고쳐졌다고
믿는 취약점이고, 이 시스템이 만들 수 있는 최악의 산출물입니다. 보류는 작업
항목입니다 — plan agent가 그 blueteam을 **병합된 트리** 기준으로 재배정하면
다른 수정이 이미 들어가 있으므로 충돌이 사라집니다.

**제출은 원자적입니다.** 두 파일을 건드리는 제출에서 한쪽이 충돌하면 전체가
보류됩니다. validator는 그 편집들을 **묶어서** 검사했지 하나만 검사한 게
아니므로, 절반만 적용하는 것은 아예 적용 안 하는 것보다 나쁩니다.

**통합본은 반드시 재검증됩니다.** `publish()`는 validator 판정 없이는 버전을
끊지 않고, 거부된 판정이면 아무것도 내보내지 않습니다. 오퍼레이터가 업로드하는
것은 개별 blueteam의 산출물이 아니라 **이 모듈의 산출물**입니다.

**바이트로 다룹니다.** 번들 파일이 유효한 UTF-8이라는 보장은 없고, v1 루프는
그런 파일을 디코드하다 `UnicodeDecodeError`를 낸 적이 있습니다.

### mutation 스위트가 잡아낸 것

두 가지가 테스트에 의해 바로잡혔습니다:

1. **중복 가드.** 첫 구현은 모든 범위 쌍을 미리 겹침 검사했는데, mutation
   스위트가 **그 검사를 통째로 지워도 어떤 체크도 알아채지 못한다**는 것을
   보여줬습니다 — 뒤따르는 커서 검사가 이미 같은 모양을 거부하고 있었기
   때문입니다. 이웃과 구별되지 않는 가드는 심층 방어가 아니라 **보장처럼
   읽히는 미검증 코드**입니다. 지웠습니다.
2. **레포트 조회 버그.** `by_id`는 취약점 ID로 키가 잡혀 있는데 경로로
   조회하고 있었습니다. 파일 하나에 취약점이 여럿일 수 있으므로 경로는 키가
   될 수 없습니다.

이력 파일은 `live_fire_patch_loop`가 쓰는 것과 **같은 모양**입니다. 오퍼레이터의
job UI가 이미 그 이력을 렌더하고 버전별 피드백을 받고 있으므로, 다른 포맷을
만드는 것은 같은 질문에 두 번째 UI를 만드는 일입니다. 달라진 것 하나는
`verified`가 드디어 참이 될 수 있다는 것입니다 — v2에는 실제로 검사한
validator가 있으니까요.

## 통합 검증 — 네 모듈을 처음으로 함께 돌림

지금까지는 조각별로만 돌았습니다: stack과 validator는 실제 스택에, repo와
orchestrator는 **제가 직접 쓴 fixture와 fake runner**에만. 그래서 세 이음매가
한 번도 검증된 적이 없었고, 그것은 `serves` 접두사 버그와 **정확히 같은
부류**입니다 — 세 컴포넌트가 경로 네임스페이스에 합의하는 이유가 "같은 사람이
셋 다 썼기 때문"인 상황.

실제 `base.zip`에서 워크스페이스를 만들고, bf8d00c76ed8의 실제 패치로
`PatchSubmission` N개를 만들어, `integrate → materialise → validate → publish`
를 **실제 `build_patched_zip`**으로 돌렸습니다.

```
workspace: K members
base_files resolved N/N paths from the real workspace     ← 이음매 1
merge: accepted=N deferred=0
materialised N files into the real manifest-backed candidate  ← 이음매 3
validator: waiting <N>s for the clock to turn over
INTEGRATED VERDICT ok=True unexplained=0
repo: V1 — N vuln clear, 0 deferred, sha (생략)     ← 이음매 2
zip: K entries, 패치된 파일이 패치본과 바이트까지 일치
remaining: (N, 'N of M still to find')
```

### 첫 통합 실행이 찾아낸 결함

첫 시도는 설명되지 않은 차이로 실패했습니다. 원인은 granularity가 base 캡처
사이 간격보다 긴, 시계에서 파생된 필드였습니다: base 캡처들이 그 필드의 같은
구간 안에 떨어지면 calibration은 그 줄을 "고정"으로 배우고, 구간이 넘어간 뒤의
patched 캡처가 시계 탓을 뒤집어씁니다.
이것이 앞서 "재현되지 않아 원인을 못 봤다"고 기록한 flake의 **정체**입니다.

변동성에는 두 원천이 있고 노출 방법이 다릅니다:
- **요청별**(nonce, 세션 id, autoincrement) — 아무 두 캡처 사이에서나 드러남
- **시계별** — 그 필드의 granularity보다 **긴 간격**이 있어야 드러남

그래서 base를 **세 번** 캡처합니다: 스택 A 한 번, 스택 B에서 두 번인데 두
번째는 **분 경계를 넘긴 뒤**. 모든 캡처 쌍이 비교되므로 어떤 필드든 **한 번만
변하면 영구히 제외**됩니다. 비용은 잡당 최대 61초이고, 이미 분 단위인 establish
임계 경로 위에 있습니다.

## Phase 3b 결과 — 오케스트레이션 (완료)

`modules/live_fire_orchestrator.py` + `scripts/test_live_fire_orchestrator.py`
(baseline 33 검사 / mutation 17개 전부 포착).

validator와 repo가 각자의 절반을 소유합니다. 이 모듈은 둘 다 볼 수 없는 것을
소유합니다 — **어떤 취약점이 진행 중이고, 각각에 무슨 일이 있었고, 스택을 동시에
몇 개까지 띄울 수 있는가**.

### 취약점은 조용히 버려지지 않는다

패치가 번들에 도달하지 못하는 경로가 셋인데, **각각 다음 조치가 다릅니다**:

| 경로 | 다음 조치 | 시도 횟수 차감 |
|---|---|---|
| 병합이 **보류**했다 | 그대로 재시도 — 진 상대의 수정이 이미 트리에 들어가 있어 충돌이 사라짐 | **안 함** |
| validator가 **거부**했다 | plan agent가 새 패치 방향을 줘야 함 | 함 |
| 시도 횟수 **소진** | 오퍼레이터에게 보고 (`exhausted`) | — |

셋을 하나로 뭉개면 취약점 하나가 조용히 작업 대상에서 빠지는데 카운트는 여전히
진행도로 읽힙니다. 특히 **보류에 시도 횟수를 차감하지 않는 것**이 중요합니다 —
그 blueteam의 예산을 남의 충돌에 쓰는 셈이기 때문입니다.

재관측(re-sighting)은 **새 방향은 받되 시도 횟수는 유지**합니다. 리셋하면
에이전트가 같은 버그를 계속 재보고해 무한히 돌 수 있습니다.

### 슬롯 예산은 역할별이 아니라 전체다

blueteam 검증 N개 + 통합본 검증 + base 재캡처가 **같은 풀**을 씁니다. 세마포어로
강제하는 이유는, 막으려는 실패가 "이 잡이 느려지는 것"이 아니라 **docker 주소
풀이 고갈되어 호스트의 다른 모든 잡이 시작조차 못 하는 것**이기 때문입니다.

### 신호 둘은 서로 다른 것을 말한다

- `known`: 잡 생성 때 오퍼레이터가 입력한 개수
- `blocked`: 채점 서버가 돌려주는 "막은 공격 수"

통합된 수정이 3개인데 막은 공격이 1개면 그것은 "2개 더 찾아야 함"이 **아닙니다**.
**수정 하나가 버티지 못하고 있다**는 뜻이고, 다른 문제이며 다음 조치도 다릅니다.

### 개별 검증 + 통합 검증, 의도적 선택

더 싼 설계는 통합본만 검증하는 것입니다(라운드당 스택 1회 vs N회). 거부한
이유는, 그러면 나쁜 패치 하나가 번들 전체를 떨어뜨리는데 **어느 것인지 아무도
말해주지 않기** 때문입니다. "뭔가 깨졌다"는 라운드는 아무도 조치할 수 없습니다.
개별 검증이 라운드 비용의 대부분이지만, 실패를 귀속 가능하게 만드는 것이
바로 그것입니다 — repo agent가 보류의 충돌 상대를 명시하는 것과 같은 이유입니다.

### 순차일 수밖에 없는 것

`validator.establish()`는 어떤 blueteam이 제출하기도 전에 끝나야 합니다. 모든
`validate()`가 그 베이스라인 기준으로 판정되기 때문입니다 — base 스택 2개를
연달아 띄우므로 분 단위이고, 병렬화가 이득을 내기 전에 임계 경로에 놓입니다. 취약점 식별은
이것과 겹칠 수 있지만 패치는 못 겹칩니다.

## Phase 2 설계 메모 — validator agent

Phase 1이 런타임을 줬으니, validator agent는 그 위에서 **코퍼스를 스스로
만드는 일**을 합니다. 오퍼레이터 사양: "최초 base 코드를 기반으로 서비스의
정상적인 요청/응답 쌍을 생성하고 plan agent에 정보공유".

### 코퍼스 생성은 스스로를 검증해야 한다

에이전트가 소스를 읽고 요청을 제안합니다. 그것을 **두 base 스택에 각각
돌려서** 안정적이지 않은 요청은 떨어뜨립니다. 그리고 **떨어뜨린 것을
보고합니다** — 조용히 줄인 코퍼스는 "다 검사했다"로 읽히기 때문입니다.
`compare(min_checked=)`를 validator가 실제로 올려 잡습니다. 기본값 1은
문자 그대로 0인 경우만 막습니다.

### Phase 1에서 확정된 제약

| 제약 | Phase 2에 미치는 영향 |
|---|---|
| 동시 스택 상한 ≈ (주소 풀 − 사용 중) ÷ 스택당 네트워크 수, 안전선은 그보다 낮게 | blueteam fan-out에 **슬롯 예산 + 대기열** 필요 |
| 스택 하나 up→ready 시간도 짧지 않음 | 검증 1회 비용이 분 단위. 짧은 Tick 안에 몇 회 도는지가 설계 변수 |
| 메모리는 제약 아님 | 슬롯 수를 RAM으로 정하지 말 것 |
| 준비 게이트에 DB 페이지 필수 | 생성된 코퍼스가 준비 집합을 겸할 수 없음 — 별도로 지정해야 함 |
| 앞단 프록시를 거치지 않는 서비스가 있을 수 있음 | 내부 서비스 검증은 별도 프로브 대상 |

### 아직 답 안 된 것

- **정적 자산 변경은 정책 손잡이가 아니라 오탐 부류다 — Phase 2의 차단 요소.**
  앞으로 밀어보면 분명합니다: blueteam이 그대로 서빙되는 파일을 고친다 →
  validator가 코퍼스를 재생한다 → 그 파일을 서빙하는 요청이 실패한다 →
  validator가 패치를 거부한다 → repo agent는 그걸 받지 못한다.
  **서빙되는 파일을 고치는 수정은 전부 이렇게 죽습니다.** 공격 서버가 정말로 정적
  자산을 바이트 비교한다면 문제 자체가 풀 수 없는 것이 되므로, 현실적인 해석은
  비교하지 않는다는 쪽입니다.

  인코딩해야 할 구분은 "정적 자산 제외"가 아닙니다:
  **패치 자신의 변경 집합 안에 있는 경로를 직접 서빙한 것은 설명된 변경이고,
  그것을 include할 뿐인 렌더 페이지는 움직이면 안 된다.**
  이 모양은 이미 `live_fire_patch_loop._unexplained_paths(findings, diffs)`에
  있습니다. 4-agent 설계에서 validator는 blueteam의 diff를 인수받으므로 같은
  방식으로 분류할 수 있습니다 — 정적 자산 요청이 바뀌었고 그 파일이 `changed_paths`에
  있으면 **설명됨**; 렌더된 페이지가 바뀌었고 그 소스가
  `changed_paths`에 있어도 **여전히 위반** — SLA 표면은 파일의 바이트가 아니라
  페이지의 렌더 결과이기 때문입니다.
  validator가 `compare()`를 게이트로 쓰기 **전에** 이 규칙을 정해야 합니다.
- **worker 안에서의 `config --format json`**. 호스트는 `v5.3.1`로 검증했지만
  worker는 apt의 `docker-compose-plugin`을 받습니다. 빌드 라인이 다르므로
  재빌드 후 **통합 전에 명시적으로 확인**해야 합니다. 이 플래그 하나가 모듈
  전체를 떠받칩니다.
- worker 이미지 재빌드는 `13dc28b96d38`이 끝난 뒤. 지금은 프로덕션에서
  이 모듈을 쓰지 않으므로 급하지 않습니다.
- 사소: `wait_tcp`가 `ready_timeout_s`를 통째로 쓰고 `wait_ready`가 다시
  새로 시작하므로, 300을 준 호출자가 최대 600을 기다릴 수 있습니다. 다음에
  이 파일을 건드릴 때 마감 시각을 공유하도록.

### 막힌 것 — 새 이미지 롤인

**`deploy.sh --worker`로는 반영되지 않습니다**: 그 스크립트는 `compose restart`를

파이썬은 bind mount라 restart로 충분하지만, **Dockerfile 변경은 이 경로로 배포될
수 없습니다.**

지금 재생성할 수 없는 이유는 별개입니다: `13dc28b96d38`(rev, 01:33 UTC 시작,

어느 슬롯인지 특정할 수 없습니다. `deploy.sh`의 fail-closed 규칙이 이 경우를
명시적으로 다룹니다 — "슬롯 없음은 '어느 슬롯이든 가능'이지 '바쁜 슬롯 없음'이
아니다". 그래서 아무것도 재생성하지 않았습니다.

**그 잡이 끝난 뒤 한 줄:**

```
PATH=/snap/bin:$PATH docker compose -p hextech_ctf_tool up -d \
  worker-1 worker-2 worker-3 worker-4 worker-5 worker-6 \
  worker-7 worker-8 worker-9 worker-10 worker-11 worker-12
```

`up -d`여야 합니다(`restart` 아님). 이미지가 바뀌었으므로 compose가 재생성합니다.
